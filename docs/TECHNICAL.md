## 全体の構成

```
           ┌────────────── RP2354A (KagigataDisk) ───────────────┐
 CLK ─────▶│ pio0 sm0  sd_cmd   CMD の受信・応答 ◀─▶ core1        │
 CMD ◀────▶│                                    (RAM のみで実行)  │
 DAT0 ◀────│ pio1 sm0  sd_dat   DAT0 ブロック送信 ◀── DMA         │
 DAT3 ────▶│ GPIO 入力（プルアップ）                              │
           │ pio2      selftest 用のホスト役（通常は未使用）      │
           │ core0: クロック初期化、USB CDC コンソール、LED、     │
           │        ログとフラッシュ保存、設定                    │
           └──────────────────────────────────────────────────────┘
```

| 担当 | 内容 | ファイル |
|---|---|---|
| core1 | PIO から受けたコマンドを解釈し、応答とデータブロックを返す。**RAM だけで動く**ので、core0 がフラッシュを書いている間も止まらない | `src/sd_responder.c`, `src/sd_proto.c` |
| core0 | クロック設定、USB コンソール、LED、ログの表示とフラッシュ保存、設定の読み書き | `src/main.c`, `src/sdlog.c`, `src/config.c` |
| pio0 | CMD 線の受信（48bit）と応答（48 / 136bit） | `src/sd_cmd.pio`（`sd_cmd`） |
| pio1 | DAT0 のデータブロック送信。DMA で供給 | `src/sd_cmd.pio`（`sd_dat`） |
| pio2 | 自己診断のときだけ、ホスト役として CLK を出して DAT0 を読み返す | `src/sd_cmd.pio`（`sd_selftest_host`） |

### フラッシュの配置（2 MiB の末尾 64 KiB）

| 位置 | 内容 |
|---|---|
| 末尾から 64 KiB〜4 KiB（15 セクタ） | ログ。コマンドを受けた起動 1 回につき 1 セクタ（ヘッダ 32 バイト + 20 バイト × 最大 203 件）を、リングとして使う |
| 末尾 4 KiB | 設定（`kg_config_t`、FNV-1a のチェックサム付き） |

ログの保存は、コマンドが 30 ms 途切れたとき、または 1 秒ごとに行います。ヘッダのページは最後に書くので、書き込み中に電源が落ちたセクタは無効として扱われます。

## SD Express のハンドシェイク

SD 7.x の仕様では、ホストは **CMD8（SEND_IF_COND）の引数の bit 12（PCIe Availability）** で、カードが PCIe に対応しているかを問い合わせます。bit 13 は PCIe 1.2V 対応の問い合わせです。カードが R7 応答で同じビットを返すと、ホストは SD Express カードとして扱い、VDD2（1.8V）を入れて PCIe に移ります。Linux の `mmc_send_if_cond_pcie()` と同じ手順です。

```
Switch 2                       KagigataDisk                  アダプタ / M.2 SSD
  │ CMD0 ─────────────────────▶ │ (応答なし)                       │
  │ CMD8 arg=0x000011AA ──────▶ │ bit12 = PCIe Availability        │
  │ ◀───────── R7 0x000011AA ── │ bit12 を返す = PCIe ACK          │
  │ VDD2 (1.8V) ON ─────────────────────────────────────────────▶ │ 信号線を SSD 側へ
  │ ◀═════════════════ PCIe / NVMe ════════════════════════════▶ │
```

- このファームが返すのは R7 までです。VDD2 を検出して信号線を切り替えるのは、アダプタ側の回路の役目です。
- PCIe ACK を返した後、KagigataDisk は CMD 線を放したままにします（応答しない）。
- 1.2V のビット（`pcie_1v2`）は、初期値では返しません。1.2V 用のピンを持たない microSD Express カードもあるためです。

## カードとしての応答

Switch 2 は PCIe を問い合わせる前に、SD モードでの初期化を何度か試します（[観察した流れ](#switch-2-で観察した初期化の流れ)）。そのため、普通の SD カードとしても応答します。

### 対応しているコマンド

| コマンド | 応答 | 備考 |
|---|---|---|
| CMD0 | なし | 状態をリセット。非アクティブ状態からも戻る（USB 給電で電源が切れない場合に備えて） |
| CMD8 | R7 | 電圧範囲が 2.7–3.6V 以外なら応答しない。PCIe ビットは上記のとおり |
| CMD55 / ACMD41 | R1 / R3 | `acmd41_busy` 回 busy を返してから ready。CCS = 1（SDHC/SDXC）。**S18A（1.8V 信号）は常に 0** |
| CMD2 / CMD10 | R2（CID） | MID = `mid`、OID = `KG`、PNM = `KGEXP`、PSN = チップ固有 ID から生成 |
| CMD3 | R6 | RCA = `rca`（0 ならチップ固有 ID から生成） |
| CMD9 | R2（CSD v2.0） | 容量 = (`c_size` + 1) × 512 KiB |
| CMD7 / CMD13 / CMD15 / CMD4 | R1b / R1 / なし / なし | |
| CMD16 | R1 | 512 以外ならエラービットを立てる |
| CMD20 / CMD23 | R1b / R1 | SCR の CMD_SUPPORT（`scr_cmd`）で申告したときだけ |
| ACMD42 | R1 | |
| ACMD6 | R1 | 1bit は常に受け付ける。4bit は `scr_4bit = 1` のときだけ |
| **CMD6** | R1 + DAT0 で 512bit | SWITCH_FUNC。mode 0（確認）と mode 1（切替）。下記 |
| **ACMD51** | R1 + DAT0 で 64bit | SCR |
| **ACMD13** | R1 + DAT0 で 512bit | SD Status |
| 上記以外 | なし | 次の R1 で ILLEGAL_COMMAND を報告する。CRC エラーも同様に COM_CRC_ERROR を報告 |

セクタの読み書き（CMD17/18/24/25 など）と CMD48/49（拡張レジスタ）には応答しません。

### レジスタの中身

| レジスタ | 内容 |
|---|---|
| OCR | 2.7–3.6V、CCS = 1、S18A = 0 |
| CSD | v2.0、TRAN_SPEED 25MHz、CCC 0x5B5、ブロック長 512、C_SIZE = `c_size` |
| SCR | SD_SPEC 2 / SPEC3 / SPEC4 / SPECX = 3（7.x）、SD_SECURITY = SDXC（容量 32GB 超）、バス幅は `scr_4bit` に従う（初期値は 1bit のみ）、CMD_SUPPORT = `scr_cmd` |
| SD Status | 現在のバス幅、C10、AU 4MB、U3、V30、A1 |
| CMD6 の応答 | 最大消費電流 100mA、各グループの対応ビット = `cmd6_fg1`〜`cmd6_fg6`、データ構造バージョン 1（busy はすべて 0） |

CMD6 は、mode 0 では各グループについて、引数の値が 0xF なら現在の機能、対応している機能ならその番号、対応していなければ 0xF を返します。mode 1 では同じ結果を返したうえで、対応していない機能が 1 つでもあれば、どのグループも切り替えません。

### 申告しないもの

- **1.8V 信号（S18A、CMD11）と UHS-I**: KagigataDisk の I/O は 3.3V 固定です。1.8V への切り替えを受け付けると、ホストが 1.8V に切り替えた信号線へこちらが 3.3V を出すことになり、ホスト側の SD インターフェースを壊すおそれがあります。設定でも有効にできません。
- **4bit バスでの転送**: DAT1/DAT2 が配線されていないので、4bit では送れません。`scr_4bit = 1` で 4bit に切り替えられた後にブロックを求められても、何も送りません（ログに `[4-bit: no block]` と出ます）。
- **High Speed（50MHz）での転送**: PIO が追従できるのは 25MHz 程度までです。`cmd6_fg1` で High Speed を申告すること自体はできます。

## 起動シーケンス

ホストはスロットに電源を入れてから数 ms で CMD0 / CMD8 を送ってくる可能性があります。SDK の標準の初期化では、main() の前に水晶発振器と PLL の立ち上げ（数 ms）が入るため、次の順にしています。

1. `PICO_RUNTIME_SKIP_INIT_CLOCKS` と `PICO_RUNTIME_SKIP_INIT_POST_CLOCK_RESETS` で、main() の前のクロック設定を飛ばす。
2. main() の最初に、ブート時のリングオシレータ（約 11MHz）のまま PIO と core1 を立ち上げる。ここから SD コマンドに応答できる。LED1 もこの時点で点灯する。
3. その後で `runtime_init_clocks()`（水晶・PLL、150MHz）と USB を初期化する。

リングオシレータで動いている間も、400kHz の初期化には十分間に合います（PIO シミュレーションで確認済み）。電源投入から LED1 点灯までの実時間は、まだ測っていません。

CMD0 には応答がなく、ホストは 8 クロック後には次のコマンドを送れます。そのため CMD0 だけは、最初の 32bit を受け取った時点で（フレームの終わりより 16 クロック前に）「応答なし」を PIO に渡しています。

## PIO プログラムと送信位相

### sd_cmd（pio0）

1. CLK の立ち上がりで CMD が Low になったらスタートビットとみなし、48bit を受信する（立ち上がりでサンプリング）。32bit と 16bit の 2 ワードを RX FIFO に入れる。
2. CPU からヘッダ（0 = 応答なし、それ以外 = ビット数 − 1）を受け取る。
3. 応答を MSB から送る（autopull）。最初のビットはコマンドのエンドビットから 2 クロック以上後にするので、NCR ≥ 2 が保たれる。
4. エンドビットが読まれたら CMD を放す。

48bit / 136bit の応答は 32bit の倍数ではありません。autopull が有効なとき、OSR が満杯なら PULL は何もしない、という仕様を使い、余ったビットは次のヘッダの PULL で捨てています。ビットごとのループは 4 命令なので、SD クロックは clk_sys / 6（150MHz で 25MHz）程度まで追従できます。

### sd_dat（pio1）

DMA から次の形式を受け取ります（`sd_dat_t`）。

| ワード | 内容 |
|---|---|
| 0 | スタートビットまでに待つクロック数 − 1（`SD_DAT_DELAY_CLOCKS` = 80。R1 応答が先に終わるように） |
| 1 | フレームのビット数 − 1 |
| 2 以降 | スタートビット、データ（MSB から）、CRC16（CCITT、初期値 0）、エンドビット |

### 送信位相（`cmd_phase` / `dat_phase`）

各プログラムの `launch` ラベル以降にある `wait` の極性を書き換えると、ビットを出す基準のエッジ（立ち下がり / 立ち上がり）が変わります。さらに CLK の入力同期回路を飛ばす（INPUT_SYNC_BYPASS）かどうかで、合わせて 4 通りになります。書き換えは core1 が RAM 上の命令のコピーから行うので、動作中にも変えられます（`dat_phase = 4` の掃引モード）。

| 値 | 基準のエッジ | 入力同期 | 25MHz で、立ち下がりからビットが変わるまで |
|---|---|---|---|
| 0 | 立ち下がり | あり | 約 +23 ns |
| 1 | 立ち下がり | なし | 約 +10 ns |
| 2 | 立ち上がり | あり | 約 +3 ns（立ち上がりから約 23 ns） |
| 3 | 立ち上がり | なし | 約 +30 ns |

（値は PIO シミュレーションによるもので、出力の遅れ 3 ns を含みます。）

Switch 2（約 24MHz）では、CMD は位相 0 で通り、位相 2 では CMD7 以降の R1 を受け取ってもらえませんでした。「ホストは自分の CLK の立ち上がりで読む」という単純なモデルでは位相 2 のほうが有利なはずなので、Switch 2 はもっと遅いタイミングで読んでいると考えられます。

### sd_selftest_host（pio2、自己診断用）

CLK を side-set で駆動し、立ち上がりごとに DAT0 を読みます。DMA で取り込んだビット列を、送ったフレームと照合します。

## Switch 2 で観察した初期化の流れ

1 回挿すごとに、Switch 2 は次の手順を約 320 ms 間隔で繰り返しました。CMD7 以降のバスクロックは約 22〜24MHz（実測）、それまでは約 380kHz です。

| 試行 | ACMD41 | 流れ |
|---|---|---|
| 1 | `0x51100000`（1.8V 要求あり） | CMD0 → CMD8 `0x1AA` → ACMD41 → CMD2 → CMD3 → CMD9 → CMD7 → CMD16 → ACMD42 → CMD13 → ACMD51 → CMD6 `0x00FFFFFF` → 中断 |
| 2 | `0x51100000` | 試行 1 と同じ |
| 3 | `0x50100000`（1.8V 要求なし） | 試行 1 と同じ |
| 4 | `0x50100000` | … → ACMD51 → ACMD13 → ACMD13 → 中断 |
| 5 | — | **CMD0 → CMD8 `0x11AA`（PCIe の問い合わせ）** → PCIe ACK → 以後 SD コマンドなし |

わかったこと:

- **PCIe の問い合わせ（5 回目）が来るかどうかは、それまでの失敗のしかたで変わります。** SD モードが SCR の読み出しまで進み、1bit のまま失敗したときだけ、5 回目が PCIe の問い合わせになりました。CMD7 で止まったとき（テスト 2）や、SCR で 4bit を申告して 4bit で失敗したとき（テスト 4）は、問い合わせが来ませんでした。
- **SCR（64bit）は正しく読まれています。** 4bit を申告すると、Switch 2 はすぐ ACMD6 で 4bit に切り替えてきました。
- **CMD6 / ACMD13（512bit）の後は、どの位相・駆動電流でも先に進みませんでした。** High Speed を申告しても切り替え要求（mode 1）は来ず、ACMD13 は毎回 2 回読まれます。チップ内での送信は自己診断で正しいことを確かめたので、原因は基板の外での波形か、Switch 2 が中身を見て打ち切っているかのどちらかです。結果的には、SD モードがここで失敗することが PCIe の問い合わせにつながっています。
- PCIe ACK の後に何が起きるかは、このファームからは見えません。

## 実機テストの経緯

ログは [`docs/logs/`](logs/) にあります（コンソールの `hist` / `log` の出力をそのまま保存したもの）。

| テスト | 変えたこと | SD モードの結果 | PCIe ACK | 画面 | ログ |
|---|---|---|---|---|---|
| 1 | 位相 CMD 0 / DAT0 0、SCR 1bit | 4 回とも CMD6 / ACMD13 で中断 | 5 回目に成功 | アクセスできない | `run1_cmd-fall_dat-fall.txt` |
| 2 | 位相を 2 / 2（立ち上がり基準）に | 5 回とも CMD7 / CMD16 で中断 | なし | アクセスできない | `run2_cmd-rise_dat-rise.txt` |
| 3 | CMD 0、DAT0 は試行ごとに掃引 | DAT0 位相 2 は SCR の直後で中断、ほかはテスト 1 と同じ | 5 回目に成功 | アクセスできない | `run3_dat-phase-sweep.txt` |
| 4 | SCR で 4bit、CMD6 で High Speed を申告 | SCR の直後に 4bit へ切替 → 中断。5 回目は 1bit で再試行 | なし | — | `run4_scr-4bit_hs.txt` |
| 5 | SCR を 1bit に戻し、DAT0 を 12mA・高速スルーレートに | 位相 2 でも SCR が通るように。CMD6 / ACMD13 は変わらず | 5 回目に成功 | アクセスできない | `run5_dat-12mA.txt` |
| 6 | CSD の容量を 512GB（10⁹ 単位）に | テスト 5 と同じ | 5 回目に成功 | アクセスできない | `run6_csd-512GB.txt` |
| 7 | CSD の容量を SSD の実容量に合わせる（差 344 KiB） | テスト 5 と同じ | 5 回目に成功 | アクセスできない | `run7_csd-matches-ssd.txt` |
| 8 | **SSD を WD PC SN530 から WD PC SN740 に交換** | テスト 5 と同じ | 5 回目に成功 | **正しく認識** | `run8_success_sn740.txt` |

テスト 1〜7 の SSD は WD PC SN530 512GB、テスト 8 は WD PC SN740 でした。テスト 8 で SD 側のやり取りがまったく同じまま認識されたことから、それまでの失敗は PCIe 側（SSD）によるものだったと考えられます。CSD の容量は、テスト 6・7 で変えても SD 側の流れに影響がありませんでした。

自己診断（`selftest run`）の結果は [`selftest_dat0_loopback.txt`](logs/selftest_dat0_loopback.txt) にあります。3 種類のクロック × 4 位相 × 4 種類のブロックの 48 通りすべてで、正しく読み返せました。

## 設定項目

コンソールの `set 名前 値` で変更し、`reboot` で反映します。設定はフラッシュに保存されます。初期値は、テスト 8 で認識できたときの組み合わせです。

| 名前 | 初期値 | 内容 |
|---|---|---|
| `pcie_ack` | 1 | CMD8 の PCIe Availability ビットを返す（ハンドシェイク本体） |
| `pcie_1v2` | 0 | ホストが聞いてきたら、PCIe 1.2V 対応ビットも返す |
| `sd_mode` | 1 | CMD8 の後の SD 初期化にも応答する。0 にすると CMD0 / CMD8 にしか応答しない |
| `check_crc` | 1 | CRC が合わないコマンドを無視する（実カードと同じ） |
| `dat3_pullup` | 1 | CD/DAT3 をプルアップする |
| `acmd41_busy` | 2 | ACMD41 に何回 busy を返してから ready にするか |
| `mid` | 0 | CID のメーカー ID |
| `cmd_phase` | 0 | CMD の送信位相（[上の表](#送信位相cmd_phase--dat_phase)）。Switch 2 で通るのは 0 |
| `dat_phase` | 4 | DAT0 の送信位相。4 は掃引（CMD0 を受けるたびに 0→1→2→3→0…） |
| `rca` | 0 | RCA。0 ならチップ固有 ID から決める |
| `c_size` | 976771 | CSD の容量。容量 = (C_SIZE + 1) × 512 KiB。初期値は 512GB の SSD（512,110,190,592 バイト）を超えない最大の値。別の SSD に合わせるなら `バイト数 ÷ 524288 − 1`（切り捨て） |
| `scr_4bit` | 0 | SCR で 4bit 対応を申告し、ACMD6 の 4bit を受け付ける。**Switch 2 では 0**（1 にすると PCIe の問い合わせが来なくなる） |
| `scr_cmd` | 3 | SCR の CMD_SUPPORT（bit0 = CMD20、bit1 = CMD23） |
| `cmd_drive` | 0 | CMD ピンの駆動。0 = 4mA・遅、1 = 4mA・速、2 = 8mA・速、3 = 12mA・速 |
| `dat_drive` | 3 | DAT0 ピンの駆動（同上） |
| `cmd6_fg1` | 0x8003 | CMD6 グループ 1 で対応を申告する機能（bit n = 機能 n）。0x8003 = Default Speed + High Speed |
| `cmd6_fg2`〜`cmd6_fg6` | 0x8001 | グループ 2〜6。機能 0 のみ |

## ログ

コンソールを開いている間は、コマンドを受けるたびに 1 行ずつ表示されます。

```
   80   21760.786ms  CMD8  SEND_IF_COND           arg=000011aa  -> R7  000011aa [PCIe ACK]  st=idle  clk=379kHz
```

| 欄 | 意味 |
|---|---|
| 先頭の数字 | 起動してからの通し番号 |
| 時刻 | 起動からの経過時間（ms）。クロック設定の前はリングオシレータ基準の概算 |
| コマンド | `CMD` / `ACMD`、番号、名前、引数 |
| `->` | 返した応答の種類と 32bit の内容（R2 は中身を省略） |
| `[PCIe ACK]` | R7 で PCIe ビットを返した |
| `+DAT0 block` | DAT0 でデータブロックを送った |
| `[4-bit: no block]` | 4bit バスなのでブロックを送れなかった |
| `[illegal]` | この状態では受け付けないコマンド |
| `[bad frame]` | フレームが壊れている（挿抜のときの接点ノイズなど） |
| `st=` | コマンドを処理した後のカードの状態（`4bit` はバス幅） |
| `clk=` | コマンドの最後の 16bit を受け取る間に測った SD クロック（25MHz で ±3% 程度） |
| `dph=` | DAT0 の位相（CMD0 の行と、ブロックを送った行に出る） |

`hist` の `first at ... us` は、最初のコマンドが届いた時刻です。この値が極端に小さい場合や、最初のコマンドが CMD0 でない場合は、起動が間に合わずにコマンドを取りこぼしている可能性があります。

## 検証の方法

| 方法 | 確かめていること | 実行 |
|---|---|---|
| ユニットテスト（`test/test_sd_proto.c`） | CRC7、CRC16（仕様書の例: 0xFF × 512 → 0x7FA1）、R7 の PCIe ビット、状態遷移、CMD6 / ACMD51 / ACMD13、バス幅、CMD20 / CMD23、CSD / SCR / SD Status の配置、DAT0 フレームのビット列、CRC エラーと不正コマンドの報告 | `gcc -DSD_PROTO_HOST_TEST -Isrc -o test_sd_proto test/test_sd_proto.c src/sd_proto.c` |
| PIO シミュレーション（`test/sim_sd_cmd_pio.py`） | ビルドした PIO 命令をサイクル単位で実行し、模擬ホストを相手に確認: 受信フレーム、応答のビット列（48 / 136bit）、NCR 2〜64、CMD0 の 8 クロック後の CMD8、CMD 線の解放、DAT0 ブロック（82 / 530bit）の連続送信。4 つの送信位相、2 通りの autopull の挙動、400kHz（ブートクロック / 150MHz）と 25MHz | `python test/sim_sd_cmd_pio.py build/sd_cmd.pio.h` |
| RAM 常駐チェック（`tools/check_core1_ram.py`） | core1 から呼ばれる関数と、参照するデータがすべて RAM にあること | `python tools/check_core1_ram.py build/kagigatainject.elf [objdump のパス]` |
| 自己診断（`selftest run`） | 実機のチップ上で、PIO・DMA・ピンを通った DAT0 のブロックが正しいこと | コンソールで実行（**アダプタから抜いて**） |

RAM 常駐チェックで実際に見つかった問題:

- **CRC7 のテーブル**: 書き換えない配列だったため、GCC がフラッシュに置いていました。`__not_in_flash` で RAM に移しました。
- **memset**: Pico SDK 2.3.1 / GCC 15 でビルドすると、ゼロ埋めのループが、フラッシュにある `memset` の呼び出しに変換されていました（SDK 2.3.0 / GCC 14 では RAM 上でした）。core1 のソースを `-fno-tree-loop-distribute-patterns` でコンパイルするようにしました。

## 制約と未解決の点

- **SSD の相性**: WD PC SN740 は認識されました。WD PC SN530 512GB は、ハンドシェイクが成功しても認識されませんでした。原因（電源、PCIe のサイドバンド信号、そのほか）は特定できていません。
- **SD モードの 512bit ブロック**: Switch 2 の CMD6 / ACMD13 に対する応答が受け入れられているかどうかは、わかっていません。
- **起動時間**: 電源投入から応答できるまでの時間は実測していません。VDD と LED1 をオシロで同時に見れば測れます。
- **バスの制約**: 1bit のみ、25MHz 程度まで、3.3V 信号のみ。セクタの読み書きはできません。
- **電源**: KagigataDisk の USB-C とカード端子の 3.3V を同時につなぐと、アダプタの回路によっては電源がぶつかるおそれがあります。
